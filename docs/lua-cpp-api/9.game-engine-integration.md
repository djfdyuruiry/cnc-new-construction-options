# Game Engine Integration

This document covers how the C&C game engines integrate with the Lua functionality.

_Note: Red Alert is not supported yet_

## Tiberian Dawn

The main integration point for TD is the [`ScenarioLua`](../../tiberiandawn/lua/scenariolua.h) class, which manages the Lua Engine for the game.

### On Scenario Load

- When a new scenario is loaded by `Read_Scenario_Ini(..)` in [scenarioini.cpp](../../tiberiandawn/scenarioini.cpp) `ScenarioLua::On_Scenario_Load(..)` is called with Scenario variables
- The `LuaEngineBuilder` is then used to create a Lua engine with all the required APIs
- `ScenarioLua::Exec_Scenario_Lua_Scripts(..)` then tries to load lua scripts based on the current scenario variables (See comment on that method for details)
- Errors executing any of the scripts are logged (but do not prevent the mission from starting)

### Lua Events

To maintain thread safety any actions that change the game engine state are captured as events. These are classes in `tiberiandawn/lua/events` that hold small pieces of logic and data. 

Specifically these events are used to write data and modify UI state, as doing this at a random point in a background thread might cause corruption or crashing.

#### Event Flow

- The Lua APIs create an instance of an event class and add it to to the global queue `LuaList`
  - This queue is an instance of [AtomicQueue](../../common/atomicqueue.h), which prevents two threads from modifying the queue at once
  - Two independent Lua threads can try to schedule events, but it's treated as first come first serve (priority can't be guaranteed)
- Every time TD renders a frame, it calls `Execute_DoList(..)` in [queue.cpp](../../tiberiandawn/queue.cpp)
  - This means this function is called 60 times a second
- `Execute_DoList(..)` calls `ScenarioLua::Process_Lua_Events(LuaList)` to trigger the processing of Lua Events
- `Process_Lua_Events(...)` executes each item in the list in a FIFO manner (first in, first out), ensuring that events happen in the correct order
  - Order is import here, as a request to do X might be cancelled out be another request to do Y - what matters is that the game state is correct at the end of processing 

### Triggers

TD uses triggers to program scenario behavior, and NCO added two new trigger actions for Lua:

- `Lua Event` - A Lua function will be registered for callback when the event triggers
- `Lua Script` - A script file will be executed when the event triggers

Both of these are processed by the `TriggerClass::Spring(..)` method in [trigger.cpp](../../tiberiandawn/trigger.cpp), which passes in the name of the associated trigger to the Lua event handlers.

#### Lua Event

- The `ScenarioLua::Exec_Event_Trigger(..)` method is called, which uses the `EventLuaApi::Execute_Event(..)` method to attempt to call the relevant Lua function, see [event_luaapi.h](../../common/lua/event_luaapi.h)

#### Lua Script

- The `Scenario::Exec_Script_Trigger(..)` method is called, which uses the `LuaEngine::Exec_File(..)` method to attempt to execute the relevant Lua script, see [luaengine.h](../../common/lua/luaengine.h)
