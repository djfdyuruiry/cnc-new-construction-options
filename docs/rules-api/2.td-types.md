# Tiberian Dawn Types

This document details the C++ types that are adapted to work with NCO rules API. Tiberian Dawn extensively uses enums to
identify instances of types. For example, there is `INFANTY_E1` for Minigunners. These are stored inside class instances 
to allow game code to quickly determine the type of the object.

In the original C&C code this is used to iterate over instances of a given type efficiently, for example in the `UnitTypeClass` 
the `Type` field holds a `UnitType`, then the static `Pointers` array holds `UNIT_COUNT` instances. You can then loop from 
`UNIT_FIRST` to `UNIT_LAST` to visit each instance of the `UnitClassType`.

## Class Structure

- At the top level you have a `XTypeClass` (e.x. `BuildingTypeClass`)
  - Each object of this class holds static properties for a given instance type
  - These are typically defined as static objects in `xdata.cpp` files (e.x. `bdata.cpp`)
  - They are then declared as items in the `Pointers` static member array
- Then there is `XClass` (e.x. `BuildingClass`)
  - Each object of this class represents an actual thing in the game (Unit, Infantry etc.)
  - It has dynamic properties for state (health, AI tracking data etc.)
  - Each object will hold a const pointer to the `XTypeClass` instance which defines it's static behaviour
  - These are created when a scenario INI file is read or a house builds a unit, places a building etc.

### Hierarchy

There are common base classes across type classes:

- `TechnoTypeClass` is the base class for most House based objects (Buildings, Units etc.)
- `ObjectTypeClass` is the base class for `TechnoTypeClass` and multiple other type classes that don't inherit `TechnoTypeClass`
- A few type classes have no base class, often these are ones that were never intended to be in INI files etc. (not even Scenario INI)

## Type Rules

Based on the class structure we can define rules for types by changing the properties of the `XTypeClass` instances. Using the 
existing framework from [Rule Sections](1.rulesections.md), the rules for each instance of a type can be loaded by a `RuleSection` 
instance.

- Each Type (Infantry, Unit, Building etc.) is defined as a `RuleSections` instance (a collection of sections, each representing a type instance)
- Using the INI name stored given to each instance, we look up the section by that name
- We then use the `TdTypeConverter` class to convert to/from the enum types (`WeaponType`, `HouseType` etc.) for properties that are not numbers/booleans/strings

NCO follows a similar pattern to Red Alert, adding the following methods to each type class:

```c++
// Read properties from a INI file into a `RuleSection` instance using the `IniRuleContext` wrapper (and `TdTypeConverter`, as needed)
const IniRuleContext& Read_INI(const IniRuleContext& ini) override;

// Read properties from a `RuleSection` instance directly (and `TdTypeConverter`, as needed)
const RuleSection& Read_Rules(const RuleSection&) override;
```

- The `RulesClass` calls these methods for each instance of each type in the `Init_Types()` method
- This reads type instances from an INI file with the name of the type (e.x. `infantry.ini` has a section per instance of `InfantryTypeClass`)
- There is an overload, `Init_Types(CCINIClass ini)`, which accepts an arbitrary INI file and reads instances of all types from that file
  - This is used to read rules for type instances from a Scenario INI file (Red Alert style) 

## On Change Callback

Using the `std::function` callback offered by the `RuleSection` class, type instance properties are reloaded using `Read_Rules` type class method 
if the associated section changes. This callback is set up in the static function `Init_Type` in [tiberiandawn/rules.cpp](../../tiberiandawn/rules.cpp).

This ensures that if the rules are changed at runtime by C++ code or the Lua API, the C++ type values are loaded in as expected without having 
to locate the type instance and call the `Read_Rules` method.

## Code Generation

- Properties for each type class are defined as JSON files in [tiberiandawn/types](../../tiberiandawn/types)
- These are used to generate C++ code and wiki documentation
- [cmake/NcoTypes.cmake(../../cmake/NcoTypes.cmake) is a CMake script that runs before build that generates the C++ code for type classes:
  - A template, [tiberiandawn/types-nco.cpp.in](../../tiberiandawn/types-nco.cpp.in) is rendered to [tiberiandawn/types-nco.cpp](../../tiberiandawn/types-nco.cpp)
  - Contains the two methods for each type class to read rules based on JSON properties
  - Extra logic required to read special properties is also in the template
  - Template code ensures base class properties are read as well (`TechnoTypeClass` also reads properties for it's base class, `ObjectTypeClass`)
