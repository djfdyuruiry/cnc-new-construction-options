# Rule Sections

In the common library, NCO has added a set of classes designed to build on top of the existing rules code to make reading large amounts of INI sections and mapping to C++ types easier.
These classes are found inside [common/rulesections.h](../../common/rulesections.h)

> See the comments at the top of [common/rulesections.h](../../common/rulesections.h) for an overview of class hierarchy

`RuleSection` class:
  - Allows processing entries from an INI file section and store these in memory
  - Use of templates and `std::variant` to allow reading/writing values to a rule section in memory using concrete types found in the game code (rather than calling individual `INIClass` methods)
  - Supporting more numeric types other than int and fixed - char/uchar, uint, and float - with value validation on Load from INI based on `std::numeric_limits` and `std::stoX` functions
  - Caching of all rules loaded from INI using the STL library, so you can lookup, query and set values at any time (not just when loading rules using `RulesClass`)
  - Validation of string values using `std::function` lambdas (See type converter docs below)
  - Fluent interface for chaining method calls to lots of setup in a readable way
  - Can write out stored entries to an INI
  - A `std::function` callback can be used to run some code every-time the value for an entry is changed  (used to update data that is calculated based on rule values - e.x. `SpecialClass`)
    
`IniRuleContext` class:
  - Combines an instances of `RuleSection` and `INIClass` into a wrapper - to make loading from an INI file easier
  - Fluent interface for loading entries from a section with default values
  - Supports loading entries using converters to load more types than the original `CCINIClass` supports

`RuleSections` class:
  - Stores multiple `RuleSection` instances to map out an entire INI file in memory
  - Dynamic adds new sections on entry value load
  - Used in `RulesClass` to store INI file data for `rules.ini` and types (e.g. `infantry.ini`, `unit.ini`)

## Type Converters

Rule values support numbers, bools and strings - but the game engine types often used enums to represent types and their instances; InfantryType with E1 instance for example.
To make using these types as rule values, we must serialize them to strings for storing in the INI and de-serialized them back when loading the INI rules; E1 has a Primary weapon of M16 - which is a WeaponType enum instance for example.

The `TypeConverter` C++ concept declared in `rulesections.h` describes a static class that can be used to convert between strings and these C++ types.

For actual type conversion, the below methods are important:

- `Try_Parse` to attempt to parse a string as an instance of a type
- `Try_Parse_Csv` to attempt to parse a csv string as a list of instances of a type
- `To_String` to dump an instance of a type as a string
- `To_Csv_String` to dump a vector of type instances to a csv string

There are methods for 'reflection', to work with metadata rather than conversion:

- `Get_Valid_Strings` and `Get_Valid_Instances` to get all valid instances of a type
- `Get_Default_Value` to get a default instance for a type (Should be `NONE` for most game enums)
- `Get_Type_Name` to get the name of a type as a string

A type converter is also responsible for tracking the game engine type for given rules. This is used when setting a rule at
runtime, to ensure the correct type is being used. The methods involved:

- `Register_Rule_Type` to register that a string rule has an associated C++ type
- `Register_Csv_Rule_Type` to register that a string rule has an associated C++ type, and requires a list of values; list of HouseType instances that can build a Unit for example.

> These methods are just what the common library requires, concrete implementations of the `TypeConverter` concept can expose additional methods

## Tiberian Dawn Integration

- `rulesections.h` is integrated with Tiberian Dawn inside the `RulesClass` class, the `Sections` member stores all the sections and entries from the `rules.ini` class.
- This is how NCO game rules are loaded and stored, other code in the game engine references `Sections` to look up rule values - the macros in `rules.h` simplify this (e.x. `Get_Int_Rule`)
- The global instance of `RulesClass`, `Rule`, is initialised in the `Init_Game` function in [tiberiandawn/init.cpp](../../tiberiandawn/init.cpp)

### On Change Callbacks

A `RuleSections` callback is registered by `RulesClass` to update static properties when rules change at runtime, this ensures the `SpecialClass` reflects the current rules at all times (See `RulesClass::Apply_Special_Properties`)

### `TdTypeConverter` Class

An implementation of the `TypeConverter` concept can be found in the TD code: [tiberiandawn/typeconverter.h](../../tiberiandawn/typeconverter.h)

- The `SupportedByTdTypeConverter` lists the C++ types supported by the class
- The `ConverterTypeVariant` variant is used to store information about the C++ type for a rule (When `Register_Rule_Type` or `Register_Csv_Rule_Type` is called)
- Variants are used in this class to allow working with rule values without having to use template methods (useful when you don't know the type for a rule)
  - `Get_Rule_Variant` and `Get_Csv_Rule_Variant` get a variant which holds the type for a registered rule
  - `Set_Rule_With_Variant` and `Set_Csv_Rule_With_Variant` provide wrappers around `RuleSection` to set a registered rule value at runtime
  - `Get_Type_Name_Variant` gets the type for a variant as a string
- Rule type registry is stored in `TdTypeConverter::RegisteredRuleTypes` and `TdTypeConverter::RegisteredCsvRuleTypes`
- Macro methods provide templates for calls to IniRuleContext using the converter (useful for setting fields using the callback methods from `IniRuleContext`)
- In [tiberiandawn/typeconverter.cpp](../../tiberiandawn/typeconverter.cpp) the mappings between type instances and strings are defined
  - These prefer the INI name for a type instance over the name of the enum instance (makes INI files easier to understand)
  - Macros are used to prevent code repetition, the prefix for an instance is stripped (e.x. `INFANTRY_E1` becomes `E1`)
  - This means that names and types are not coupled to object instances (original C&C code loops through Class instances and matches strings by INI name)

For more details see: [Tiberian Dawn Types](2.td-types.md)

## Code Generation

All sections inside of `rules.ini` are stored as JSON files inside [tiberiandawn/rules](../../tiberiandawn/rules).

This keeps rules in a single place, bundling comments and defaults so we can both generate C++ code and wiki documentation for rules.

Each file includes:

- Info on section (name, comment etc.)
- Rules in section
  - Name
  - Type
  - Default Value
  - Comment

The JSON Schema for these files can be found in: [cmake/nco-rules-json-schema.json](../../cmake/nco-rules-json-schema.json)

---

There is a cmake file that generates C++ code based on these JSON files: [cmake/nco-rules-json-schema.json](../../cmake/NcoRules.cmake)

- The template [tiberiandawn/rules-nco.cpp.in](../../tiberiandawn/rulekeys-nco.h.in) generates [tiberiandawn/rules-nco.cpp](../../tiberiandawn/rulekeys-nco.h) to define string macros used by `RulesClass` and game engine code to lookup rules at runtime
- The template [tiberiandawn/rules-nco.cpp.in](../../tiberiandawn/rules-nco.cpp.in) generates [tiberiandawn/rules-nco.cpp](../../tiberiandawn/rules-nco.cpp) to read rules with defaults and provide the callback to apply rules to the `SpecialClass`
